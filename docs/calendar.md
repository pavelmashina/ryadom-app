# Календарь: нормализованное хранение (issue #2)

С миграции `20261111120000_calendar_source_of_truth.sql` календарь хранится в таблицах, а не в `pets.data`.

## Модель

| Таблица | Что хранит |
| --- | --- |
| `calendar_events` | Событие или серия: название, категория, тип, дата начала, локальное время, IANA-часовой пояс, автор (`created_by`), порядок |
| `recurrence_rules` | Одно правило на повторяющуюся серию: частота, интервал, дни недели, число месяца (32 — последнее), окончание never/date/count. Его же используют графики тренировок (`source_type='training'`) |
| `calendar_event_exceptions` | Изменения одного вхождения по запланированной дате: отмена, перенос (`moved_on`), изменённые поля «только это» (`override_payload`: name, time, note, kind, category) |
| `calendar_event_completions` | Отметки «выполнено» по дате показа |

Вхождения не хранятся. Их считает `pet_private.event_occurrences(event, from, to)` только на запрошенный диапазон. Для клиента есть `public.calendar_occurrences(pet, from, to)` — не больше 400 дней. Тот же расчёт использует отправка push (`enqueue_due_push`), поэтому напоминание о перенесённом или изменённом вхождении приходит в его собственное время и с его названием.

Локальная дата и время переводятся в момент через часовой пояс события: `(день + время) at time zone timezone`. Время по часам сохраняется при переходах DST. Несуществующее время (02:30 в ночь перехода на летнее) PostgreSQL сдвигает вперёд, на 03:30. Ежегодная серия от 29 февраля в невисокосные годы приходится на 28 февраля, как и в клиентском движке.

## Чтение и запись

- `load_shared_state` собирает `events` и `done` из таблиц в прежнем JSON-формате (`domain.ts eventSchema`), так что клиенту не нужна отдельная загрузка.
- `save_shared_state` проверяет участника и ревизию, затем пишет календарь через `pet_private.store_calendar`. Клиент передаёт `updateCalendar: false`, если календарь не менялся.
- Прямые `insert/update/delete` в календарные таблицы для `authenticated` запрещены. Чтение разрешено только активным участникам неудалённого питомца (`pet_private.member_role`), поэтому после отзыва доступа данные сразу перестают быть видны.

## Клиент (`src/event-scope.ts`)

- **Только это событие** — изменение хранится в исключении серии. Id и общее напоминание серии сохраняются, отметка «выполнено» переносится вместе с датой.
- **Это и последующие** — серия заканчивается накануне выбранного вхождения, продолжение получает новый id:
  - лимит «N повторений» продолжается остатком;
  - отметки и изменения отдельных дней после границы переходят в новую серию, если шаблон повторения не менялся;
  - «последнее число месяца» и дни недели фиксируются явно.
- Новые события получают часовой пояс устройства.

## Миграция и откат

Миграция:
1. Отказывается работать, если `save_state`/`load_state`/`enqueue_due_push`/`claim_due_push` отличаются от проверенных версий (сверка по md5).
2. Копирует `events`/`done` каждого питомца в `pet_private.calendar_legacy_backup`.
3. Переносит их в таблицы и сравнивает с исходным JSON по каждому полю. При любом расхождении миграция откатывается целиком.
4. Только после этого удаляет `events`/`done` из `pets.data`.

Тренировки (`training_sessions`, оценки) миграция не трогает.

Перед применением в production: сделать бэкап базы (Supabase → Database → Backups), применить миграцию и сверить количество строк в `calendar_events`, `calendar_event_completions` с `calendar_legacy_backup`.

Тесты: `src/calendar-database.test.ts` прогоняет всю цепочку миграций в PGlite. Он проверяет перенос, доступ для владельца, редактора, постороннего и отозванного участника, переопределения, DST, 29 февраля, push и совпадение с клиентским движком.
