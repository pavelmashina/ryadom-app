# Совместный доступ к питомцу

## Как пользоваться

1. Откройте переключатель питомцев → «Совместный доступ» (также доступно в профиле).
2. Скопируйте ID вида `RYD-23456789AB` и передайте второму человеку.
3. Второй человек входит в собственный аккаунт → переключатель питомцев → «Добавить существующего питомца» → вводит ID → отправляет запрос.
4. Владелец видит индикатор новых запросов и разрешает либо отклоняет запрос в разделе совместного доступа.
5. После разрешения оба работают с одной карточкой. Участник обозначен как «Совместный доступ».

Владелец может отозвать участника, сменить ID и удалить питомца. Участник может покинуть питомца. Отзыв, выход, смена ID и удаление требуют подтверждения в интерфейсе. ID сам по себе не даёт доступ к данным. Поиск после входа возвращает только имя и состояние запроса.

## Данные и миграция

- `pets.id` приведён к UUID без изменения существующих значений. Прежний `user_id` переименован в `owner_user_id`; добавлены уникальный `share_code`, `revision`, `updated_at`, `deleted_at` и поля профиля, вычисляемые из существующих данных.
- Создана `pet_members`: уникальная пара pet_id/user_id, owner/editor, active/revoked, даты создания и изменения. У каждого существующего питомца автоматически создан active owner. Владелец единственный, обычные операции не могут убрать или заменить его.
- Создана `pet_access_requests`: pending/approved/rejected/cancelled, заявитель, даты и автор решения. Частичный уникальный индекс не позволяет создать два pending-запроса одной пары.
- `commands`, `training_sessions`, `training_command_results` используют UUID pet_id и ссылки на общую запись. Сохраняются прежние ограничения целостности результатов тренировок. Их старый user_id оставлен для совместимости ключей и обозначает первоначального владельца, а не текущего участника и не основание доступа.
- Календарь, вес, медицинские записи, запасы, документы и прежние занятия пока остаются в `pets.data`, то есть в одном JSON **конкретного общего питомца**, а не в копиях JSON по пользователям. Отдельные таблицы для этих разделов не создавались; это постепенный переход с сохранением текущего формата. Нормализованные команды и тренировки продолжают храниться отдельно.
- `account_state` хранит только персональный выбор питомца. Старый `user_state` недоступен клиентам. Старый массовый save_app_state заблокирован, чтобы устаревшая PWA не перезаписала общие данные. Старый endpoint чтения использует новые проверки членства.
- Удаление питомца устанавливает deleted_at: он исчезает у всех участников, сервер запрещает доступ, физические записи сохраняются. Обычного восстановления из интерфейса пока нет.

Миграция обновила существующие строки на месте. До и после совпали количества и контрольные суммы pets.data, commands, training_sessions и training_command_results. На момент миграции: 2 питомца, 22 команды, 1 тренировка, 21 результат. Данные не копировались между пользователями.

## ID и запросы

ID генерируется сервером из случайного UUID: 10 символов с алфавитом `23456789ABCDEFGH`, префикс `RYD-`, около 40 бит случайности. Уникальность закреплена ограничением базы; при коллизии генерация повторяется. Ввод нормализуется в верхний регистр. Символы 0/O/1/I исключены.

ID — идентификатор для запроса, а не пароль. В закрытой таблице `pet_private.rate_limits` ограничены поиск и запросы: 20 попыток в минуту на авторизованного пользователя. При смене кода старый перестаёт находить питомца; участники и уже отправленные запросы сохраняются.

Одобрение атомарно меняет pending на approved и создаёт/восстанавливает editor membership. Отказ не создаёт доступ. Повторная отправка после отказа возможна с тем же ограничением частоты. Запрос можно отменить. Отзыв и самостоятельный выход устанавливают revoked, сохраняя историю.

## Права и RLS

- RLS включён на всех таблицах. Чтение pets, commands, training_sessions и training_command_results проверяет активное членство, включая owner, и отсутствие deleted_at.
- pet_members и pet_access_requests читаются самим пользователем либо владельцем соответствующего питомца. Email участников/заявителей возвращается только владельцу через проверенную операцию manage.
- Прямая запись в таблицы питомцев и доступа от authenticated/anon запрещена. Запись идёт через узкие SQL-операции с проверкой auth.uid(), активного pet_members и роли. Editor не может через API повысить роль, добавить участника, одобрить запрос, отозвать другого человека, сменить код или удалить питомца.
- Публичные RPC являются SECURITY INVOKER обёртками. Привилегированные реализации находятся в неэкспонируемой схеме pet_private, используют пустой search_path и явные проверки. EXECUTE от PUBLIC/anon отозван. Ни service-role ключи, ни пользовательские metadata не используются в авторизации.
- Изменение прав и сохранение блокируют строку питомца. Отзыв не может конкурировать с записью таким образом, чтобы запрос, начавшийся после завершённого отзыва, продолжил редактировать данные.
- Версия каждого питомца проверяется при сохранении; устаревшая версия возвращает конфликт. Отправляются только изменённые питомцы, а не снимок всего аккаунта. Пакет изменений выполняется атомарно.

## Обновление интерфейса

Открытая активная вкладка проверяет лёгкий маркер изменений каждые 3 секунды и при возвращении в приложение. Полные данные загружаются только при изменении маркера. Это polling, не WebSocket Realtime; новые данные обычно появляются за несколько секунд при доступной сети.

Открытые формы не перезаписываются фоновым обновлением; сохранение старого черновика защищено проверкой версии. После закрытия формы подтягивается актуальное состояние. Отозванный питомец убирается даже при открытом диалоге. Сервер блокирует его немедленно после завершения отзыва; локально уже просмотренные/экспортированные данные нельзя отозвать задним числом. Списки запросов внутри диалога обновляются каждые 5 секунд.

## Проверки

- 99 автоматических тестов, в том числе 13 интеграционных сценариев PostgreSQL в PGlite: миграция, owner, lookup без утечки, pending-изоляция, повторные запросы, одобрение, общие тренировки/здоровье, конфликт версий, запрет повышения роли и добавления участников, отзыв, старые ID, смена кода, отказ/отмена/повтор, самостоятельный выход, anon, ограничение поиска и мягкое удаление.
- `supabase/tests/pet_sharing_smoke.sql` выполнен на рабочем PostgreSQL с временными пользователями внутри BEGIN/ROLLBACK. Проверены права роли authenticated, общий вес, запреты API, отзыв и смена кода. Все тестовые строки отменены.
- В браузере на изолированных ответах API: поиск → запрос → ожидание; входящий запрос → одобрение → список участников; подтверждение отзыва. Мобильная ширина 390 px без горизонтального переполнения. Реальным людям доступ во время тестов не выдавался.
- TypeScript/Vite production build проходит. Новые зависимости PGlite и типы Node используются только при разработке и тестировании, не входят в клиентскую сборку.
- Security Advisor: новых предупреждений уровня WARN/ERROR нет. INFO о rate_limits без RLS-политик ожидаем: таблица намеренно полностью закрыта и доступна только внутренней функции. [Описание проверки](https://supabase.com/docs/guides/database/database-linter?lint=0008_rls_enabled_no_policy). Прежнее предупреждение о выключенной [защите от скомпрометированных паролей](https://supabase.com/docs/guides/auth/password-security#password-strength-and-leaked-password-protection) осталось; настройки Auth этой задачей не менялись.
